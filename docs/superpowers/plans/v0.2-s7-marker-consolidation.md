# v0.2-s7 — marker-consolidation · Plan

**Date:** 2026-08-06  ·  **Branch:** `sprint/v0.2-s7`

## Context (why)

Two of this repo's stated invariants still disagree with its behaviour. `CLAUDE.md`'s
architecture map says marker spans are *the* integration seam and names one library that owns
them, but `lib/profile-block.js` still carries its own hand-rolled splice — the last of the three
implementations `lib/marker-block.js` was created to absorb, and the one v0.2-s6 deliberately
left. Separately, `mutate.js` supplies the evidence every sprint's handoff rests on, and its CLI
entry point is the one part of it no test touches. This sprint closes both, plus a legacy plan
filename that has been reported as a defect since v0.2-s2.

## Scope
- **In:** `profile-block.js` delegating its write path to `marker-block.js`; a testable CLI seam
  in `mutate.js` with tests for the wiring; renaming the legacy loop-hardening plan.
- **Out:** `upsertBlock` growing fence awareness (argued below to be unnecessary); the bootstrap
  guard's two holes; `gaw`'s missing `mutate.js`; riders 2.3 / 2.6; `.ps1` ports; the collapsed
  `execution/*` axis — all pick up in the v0.2-s7 handoff's *Deferred* section.

## Approach

**Task 1 — `profile-block.js` writes through `marker-block.js`.** The header note at
`marker-block.js:20-22` says this module is unmigrated because it "additionally guards ``` fences
— and this module does not reproduce that." That reasoning conflates two separate things.
`assertSafePayload` (`profile-block.js:82-98`) validates *inputs* — the serialized profile and
the assessment prose — before anything is rendered; `upsertBlock` never sees those values and has
no business validating them. The splice itself (`upsertProfile:115-132`) is algorithmically
identical to `upsertBlock:90-114`, trim-and-append fallback included. Only the splice moves.

The real blocker is that `renderBlock` emits `MARKER_START`/`MARKER_END` inside its own output
(`:104`, `:108`), which would trip `assertNoMarkerText`. So split `renderBlock` into a
marker-free inner renderer — heading, optional prose, ```json fence, payload — and hand that to
`upsertBlock` with `makeMarkers('asdlc:execution-profile')`. The rendered body then contains
fences but no marker text and passes cleanly. **`upsertBlock` gains nothing.**

Consequences: `renderBlock`'s own EOL normalisation (`:108`) becomes dead — `upsertBlock` does
the `\n`→eol join. `profile-block.js`'s `detectEol` (`:25-29`) is a byte-duplicate of
`marker-block.js:36-40`; re-export marker-block's rather than keeping both. `parseProfile` stays
fence-aware — it is the reader — and may take its span bounds from `findBlock` while keeping
`FENCE_PATTERN` matching on `inner`.

**Task 2 — a testable CLI seam in `mutate.js`.** Extract `runCli(argv, { cwd, log, err })`
returning an exit code; `main()` shrinks to registering the signal handlers and calling
`process.exit(runCli(...))`. This preserves what the comment at `:265-266` protects — handlers
registered inside `main` rather than at module load, so importing the module in a test installs
nothing process-wide — while making the exit-code decision, the render branch and the
restore-on-throw path assertable. Injected `log`/`err` follow the `{ runner = run }` convention
from `lib/exec.js`.

**Task 3 — rename the legacy plan.** `slugFromFilename` (`new-sprint.js:6-9`) strips
`^v[\d.]+-s\d+-`, so `v0.1-s0-loop-hardening.md` yields `loop-hardening`, matching the existing
`docs/handoffs/loop-hardening.md`. Rename the plan only; `git mv` so history follows.

  (`new-sprint.js:119`) and `compareByVersion` sorts non-canonical names oldest, so the legacy
  filename has never actually blocked the gate and does not today. The rename removes a trap that
  would fire only if that file ever became newest. Do not record it in the handoff as fixing a
  live failure — v0.2-s6's own handoff already called it "currently harmless".

  the `unmatched-plan` behaviour itself. They are fixtures, not references to the real file, and
