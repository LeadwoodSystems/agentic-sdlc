**Goal:** Make a `RED-AS-PREDICTED` mean what it says — require `expectRed` to be absent from
an unmutated baseline run before a match in the mutated run is trusted — and re-anchor the
v0.2-s3 manifest whose three verdicts currently rest on hand-reasoning.

**Architecture:** One mechanism, added to `runOne` as a precondition. `classify()` is
unchanged: the substring check was always correct *given* a discriminating anchor, and the
defect was that nothing established that premise. Two new not-evidence verdicts carry the
failures. Report vocabulary lands first (Task 1) so that no intermediate commit can return a
verdict `summarize()` treats as evidence.

**Tech Stack:** Node core only (`node:test`, `node:assert/strict`, `node:fs`, `node:path`).
No build step.

## Context (why)

`classify()` (`mutate.js:75-82`) searches the mutated run's whole `stdout + stderr` for
`expectRed`. Under `node --test`, a **passing** test prints its own title (`✔ <title>`), so an
`expectRed` naming a test is present in every run and the check degrades into "did the exit
code go non-zero" — the check it was written to replace. The pattern came from
`test-mutation-evidence.md`'s pytest example, where the anchor is a docstring and is printed
only on failure, so it holds there and fails silently everywhere else.

v0.2-s4's two anchors were re-pointed by hand once the whole-branch review found this.
`docs/mutation-manifests/v0.2-s3.json` still carries three title-shaped anchors. Until this
lands, every mutation verdict in this repo is hand-reasoned rather than measured.

```js
// One concatenation, used for both the baseline and the mutated run. They must
// be built identically: "absent from the baseline" is only a guarantee about
// "present in the mutated run" if both statements are about the same string.
function combined({ stdout, stderr }) {
  return `${stdout}${stderr}`;
}

// The unmutated run of this mutation's test command. Memoized per argv, because
// mutation cost is dominated by test bootstrap — measured in this repo at 16.7s
// for a test that builds real git fixture repos against 0.2s for a library one —
// and a per-mutation baseline would double every manifest's cost instead of
// adding one run per distinct arg-set.
function getBaseline(workdir, manifest, mutation, { runner, baselines }) {
  const args = [...manifest.testCommand.slice(1), ...(mutation.testArgs || [])];
  const key = JSON.stringify([manifest.testCommand[0], ...args]);
  if (!baselines.has(key)) {
    baselines.set(key, runner(manifest.testCommand[0], args, { cwd: workdir, env: manifest.env }));
  }
  return baselines.get(key);
}
```

## Test plan (TDD — write these first)

| Failing test | Behaviour it pins down | Tier |
|---|---|---|
| `EXPECT-RED-INERT makes the run not evidence` | A run carrying it exits non-zero and cannot be banked | pure, ~0ms |
| `BASELINE-RED makes the run not evidence` | Same, for a red baseline | pure, ~0ms |
| `both new verdicts explain themselves…` | The report says what to do, not just what happened | pure, ~0ms |
| `both new verdicts are marked as needing action…` | `!!` marks them so they don't scroll past | pure, ~0ms |
| `a test command that already fails unmutated is BASELINE-RED` | A red baseline is named, not silently absorbed into a RED | fixture + stub runner |
| `a BASELINE-RED never applies the mutation` | One invocation, no write, no borrowed duration | fixture + stub runner |
| `the baseline runs once for mutations sharing a testArgs set` | Memoized — the cost is +1 run, not ×2 | fixture + stub runner |
| `mutations with different testArgs each get their own baseline` | The memo key includes `testArgs` | fixture + stub runner |
| `an expectRed that appears in green output is EXPECT-RED-INERT` | **The v0.2-s4 defect**, reproduced without any reporter | fixture + stub runner |
| `an EXPECT-RED-INERT never runs the mutated test` | The gate is cheap and leaves no trace | fixture + stub runner |
| `the runner receives testCommand…` (strengthened) | Baseline and mutated run use identical argv | fixture + stub runner |

Per the plan template's tier rider: the four `report.js` tests are pure functions over literal
objects. The seven in `mutate.test.js` need a real file on disk for `runOne` to read, write and
revert, so they use `fixtureWithSource` — but every one of them stubs the runner, so none
spawns a test process. The real-stack coverage of the mutate loop already exists in the tests
written in v0.2-s3; these are shape variants around it.

## Risks / open questions

- **The gate protects against a systematic false positive, not a coincidental one.** An anchor
  absent from the baseline can still be matched by an unrelated failure that happens to contain
  it. Stated in the spec; the handoff should not overclaim.
- **A v0.2-s3 verdict may not survive re-anchoring.** Decided at plan time: record it, name the
  test, carry it into the next sprint. Do not let it grow a test-rewrite tail here.
- **`EXPECT-RED-INERT` can fire on a legitimate anchor** when the test command prints the
  source line it is about (a verbose reporter echoing code). The remedy is a more specific
  anchor, which is the right pressure; if it proves noisy in practice that is a finding for the
  next sprint, not a reason to weaken the gate now.
- **Baseline cost is real on slow tiers.** +1 run per distinct `testArgs` set. No opt-out flag
  by design — a gate with an off switch is off in the run whose result someone wants to believe.
- **Three mutations all target `mutate.js` while `mutate.js` runs them.** This works because
  the parent has the module cached in memory and the child re-reads it from disk (v0.2-s3's
  `REVERT` mutation is the precedent) — but if a run ever leaves `mutate.js` modified, repair
  the tree by hand before trusting anything after it.
- **No CI in this repo**, so the suite is the only gate.
