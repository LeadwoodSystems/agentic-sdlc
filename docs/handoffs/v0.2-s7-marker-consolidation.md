## Key decisions & trade-offs

- **`upsertBlock` gained nothing, and the v0.2-s6 note explaining why it must was wrong.** That
  note said `profile-block.js` could not migrate because it "additionally guards ``` fences and
  this module does not reproduce that." The fence guard runs on the *caller's inputs* — the
  serialized profile and the assessment prose — before rendering; `upsertBlock` never sees those
  values, so there was nothing to reproduce. The actual blocker was that the renderer emitted the
  markers itself, tripping `assertNoMarkerText`. Splitting out a marker-free inner renderer was
  the whole fix. A one-file change, not the two-file redesign the note implied. **A design note
  that misidentifies a blocker costs more than no note** — it priced this task out of two
  sprints. The corrected note now names the failure mode: check whether a rule belongs to the
  payload or to the span before growing the shared module.
- **The write path's unterminated message deliberately changed.** It now names the specific
  marker. Nothing asserted on the old text and no manifest anchored it (checked before changing
  it), and "no closing marker" was ambiguous in a document that can hold more than one span.
  `parseProfile`'s three read-path strings are unchanged.
- **Two shell seams in `runCli`, not one.** `assertCleanTree` needs `run()`'s throw-on-non-zero;
  `runMutations` needs `runCapture()`'s failure-is-the-measurement. One injected runner would
  hand one of them the wrong semantics — the near-miss `lib/exec.js` already documents.
- **`main()` stays untested on purpose.** It registers process-wide handlers and exits; `runCli`
  exists so `main` can stay too trivial to need a test. The handlers remain *inside* `main`, so
  importing the module still installs nothing.

## Incidents worth carrying forward

**Two of my own assertions were wrong before the code was.** The round-trip test failed because
`findBlock`'s `inner` carries the newlines adjacent to each marker while `upsertBlock` supplies
its own — feeding `inner` straight back is not an identity. And the exit-code test asserted that
a GREEN verdict is not evidence; it is. `GREEN` is pointedly absent from `report.js`'s
`NOT_EVIDENCE` set, because a mutation that was applied and reverted correctly produced a
trustworthy run — the bad news is the *finding* (a hollow test), not the run. Conflating the two
would leave the exit code unable to distinguish a hollow test from a rotted anchor, which are
opposite problems with opposite fixes. **A red test is not yet evidence the code is wrong**; both
of these were caught only by reading the failure rather than adjusting the code to satisfy it.
The GREEN case is now pinned by its own test.

**A filtered listing is not an inventory.** Mid-session the skill listing showed 5 of the
plugin's 7 commands, and I reported a missing-command defect. The listing is filtered per turn —
a `review` entry present in one turn was absent in the next with nothing uninstalled. All 7 files
were present and byte-identical in the plugin cache the whole time. **Verify absence against the
artifact, not against a rendered list.**

**The plugin runs from a cache copy, and the v0.2-s6 handoff says otherwise.** Its *Deferred*
section warns that once enabled, "commands load from the working tree — a half-edited
`commands/*.md` on a sprint branch is live in the session." That is **false**. `installPath` is
`~/.claude/plugins/cache/leadwood-local/agentic-sdlc/0.2.0`, pinned to `gitCommitSha 3f2f04a`.
The repo path in `known_marketplaces.json` is where the *manifest* is read from, not where the
plugin runs. Consequences: editing `commands/*.md` during a sprint is safe, and picking those
edits up needs a reinstall — including the ones this repo ships.

**`git mv` of a plan is invisible to the gate.** `checkGate` only inspects the *newest* plan
(`new-sprint.js:119`) and `compareByVersion` sorts non-canonical names oldest, so the legacy
filename never actually blocked anything. The rename removes a latent trap. Do not read the
Task 3 evidence as fixing a live failure — it was reproduced on a synthetic tree.

- **`runCli`'s `capture` seam is threaded but only stubbed.** No test exercises a real
  `runCapture` through `runCli`; the fixture-repo tests reach `runMutations` directly.
