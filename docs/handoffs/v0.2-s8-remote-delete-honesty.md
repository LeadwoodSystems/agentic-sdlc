## Goal

Stop `finish-sprint.js` reporting success for a remote branch delete that never happened, and
make the resulting debris visible to `/asdlc-hygiene`.

## Scope delivered

  `git config --get remote.origin.url` probe that cannot fail for network, auth, or MSYS

## Key decisions & trade-offs

- **The probe replaces a classification problem with a structural one.** `git ls-remote` exits
  128 for a missing remote, an auth failure, an unreachable network, and this machine's MSYS
  crash alike, so no amount of inspecting the error can separate them. `git config --get`
  cannot reach the network at all, so its answer is about configuration and nothing else.
- **Failures are returned, not thrown.** By the time the remote half runs, `markMerged` has
  rewritten `STATUS.md` and the local branch is gone; a throw would produce a stack trace on a
  half-applied finish. This follows `removeWorktreeForBranch`'s existing shape.
- **`deleteBranch`'s result has no `local` field.** It would always be `true` — the local delete
  either succeeded or threw — and a field that never varies is one callers learn to skip.
- **The remote audit asks the remote.** Reading `refs/remotes/origin/sprint/*` would be free and
  offline but only as fresh as the last `fetch --prune`: it reports branches already deleted and
  misses ones pushed from another clone. An audit that can be confidently wrong is what
  `.asdlc/facts.json` exists to prevent.
- **The deferred `main()` reorder is REJECTED, not deferred.** Both the spec and the plan called
  moving `deleteBranch` ahead of `markMerged` "a real improvement" put off only for test churn.
  That was wrong, and the whole-branch review caught it: `deleteBranch`'s *first* action is the
  irreversible local delete, so running it earlier makes nothing atomic — it just leaves
  `STATUS.md` saying `awaiting-merge` with the branch already deleted, which is the *less*
  recoverable half, and a re-run would then die in `resolveSprintBranch` with the sprint
  permanently unmarked. The current order is correct. **Do not carry this forward as debt.**
  The valuable generalisation is "probe everything before the first mutation" — of which
  hoisting `originUrl` (below) was the concrete instance.

## Incidents worth carrying forward

**Command prose is an ungated surface, and this sprint nearly shipped past it.** Every task
review passed, the suite was green, and `asdlc-hygiene.md` still instructed the agent to
"Present the **six** findings". `/asdlc-hygiene`'s prose *is* its executable surface, so an
agent following it could have dropped the new line entirely — shipping a detection that exists
but is never read, which is this sprint's own failure mode one layer up. **Nothing in the suite
or `asdlc-lint.js` gates a command's prose against the script it describes.** v0.2-s4 updated
this same file by hand when it added the sixth check; that discipline is the only thing holding.

**A fix can rebuild the defect it repairs, one level down.** `originUrl` correctly propagates a
non-`status===1` failure — but it was first placed *after* the local delete, so that one
surviving throw landed on exactly the half-applied finish the comment three lines above it
promised to prevent. Hoisting the probe above the mutation cost one line and no test changes.
Reading the comment against the code it guards is what found it.

**Part 2 detects the transient failure, not the standing one.** When the cause is persistent —
this machine's MSYS condition, or a dead credential — `gh-hygiene`'s own `ls-remote` fails for
the same reason and the audit prints `could not check (…)`. It cannot enumerate the debris in
precisely the recurring scenario the sprint was written for. This is not a hole: `safeCheck` +
`anyCheckFailed` make the audit exit 1, and `finish-sprint.js` has already named the branch and
printed the remedy, so the system fails loudly at both ends and never reports clean. But the
spec's phrase "the same signal Part 1 produces" understates it, and the honest statement is
this one.

## Deferred / known gaps

- **A re-run after a failed remote delete reads like a wrong-sprint-id error.** It hits
  `resolveSprintBranch` → not-found → "no branch named sprint/<id>… Nothing was changed." That
  is accurate, but the real recovery path is the `git push origin --delete` the first run
  printed. Message only; no code change proposed.
- **Both halves hardcode `origin`.** In a repo whose remote is named otherwise, finish-sprint
  reports `no-origin` (now logged) and the audit's `ls-remote origin` degrades to
  `could not check`. Consistent, but unstated anywhere outside this line.
- **`gh-hygiene.js`'s `main()` is untested generally**, so the new report line's rendering has no
  test — consistent with the file, not a regression.
- Minor, carried from task reviews: only some `deleteBranch` tests assert the full result shape
  via `deepEqual`; `parseLsRemoteHeads` silently drops a tab-less line; the corrected comment
  above `runHygieneAudit` still uses literal per-category counts; the `safeCheck` isolation test
  checks one representative sibling slot.
- Carried from v0.2-s7, untouched: `main()` in `mutate.js` untested by design; `runCli`'s
  `capture` seam threaded but only stubbed; the `--test-name-pattern` anchors depend on a test-name
  substring; `FAILING_CONCLUSIONS` is a closed set against an extensible API; `appendStatusEntry`
  appends blindly to a file not ending in a newline; `gaw` still has no `mutate.js`; the bootstrap
  guard's two holes; `--limit 50`'s cost documented only in a plan.
- Carried from v0.2-s3: riders 2.3 (`size-sprint` upstream + mutation term) and 2.6
  (verification-log storage shape); no `.ps1` ports.
